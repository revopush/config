# Generated accessors and schema branches — design

**Status:** proposed · **Affects:** `@revopush/config` core, the two repos that consume it

## The problem

`schema.json` can nest a branch — a subtree holding one deployment's keys, which only that
deployment resolves:

```json
"platform": {
  "saas":  { "cloudflare": { "uri": { "default": "", "env": "CLOUDFLARE_URI" } } },
  "azure": { "azure": { "acquisitionDailyTableName": { "default": "AcquisitionDaily" } } }
}
```

The library has no vocabulary for that, so each consumer invents one. Today both repos carry the
same flatten in two places: a `scripts/config-types.mjs` that pre-flattens into a temp schema
before calling the generator, and a `config/platform.ts` that flattens again at runtime so
`platform.saas.cloudflare.uri` reads as `cloudflare.uri`.

Two implementations of one merge, in two repos. They already drifted once — the generator used a
one-level spread while the runtime used a deep overlay, so a branch refining a common entry would
have silently dropped keys from the generated types while `--check` still passed. That divergence
is now pinned by a test in the consumer, which is the wrong place for it.

Second problem: the generated types are a flat map of dotted key to value type, and every key of
every branch lands in it. So this compiles, and throws at runtime:

```ts
config.get("cloudflare.uri"); // under PLATFORM=azure: ConfigError, unknown key
```

## The decision

1. **Keys keep their schema path.** `platform.saas.cloudflare.uri` is the key. Nothing is
   flattened, so there is no merge to implement — in the library or in a consumer.
2. **The library prunes.** At load, subtrees of a branch other than the selected one are dropped.
   Reading another platform's key throws "unknown key", as it does today.
3. **The generator emits one named interface per node**, plus a factory binding accessor objects
   to a config instance. Consumers read values through those, not through strings.

Pruning is a filter, not a recursive overlay: the semantics that drifted stop existing.

## Emitted shape

For the schema above:

```ts
// Generated by `revopush-config types`. Do not edit.

/** platform.saas.cloudflare */
export interface PlatformSaasCloudflareSettings {
  /** R2 S3-compatible endpoint */
  readonly uri: string;
}

export interface PlatformSaasSettings {
  readonly cloudflare: PlatformSaasCloudflareSettings;
}

export interface PlatformSettings {
  readonly saas: PlatformSaasSettings;
  readonly azure: PlatformAzureSettings;
}

/** Every declared key, for `createConfig` and for callers that need a dynamic one. */
export interface ConfigKeys {
  "platform.saas.cloudflare.uri": string;
  "platform.azure.azure.acquisitionDailyTableName": string;
}

/** Binds the accessors to a config instance. Kept a factory so this file imports nothing. */
export const bind = (c: ReadonlyConfig<ConfigKeys>) => ({
  platform: {
    saas: {
      cloudflare: {
        get uri() {
          return c.get("platform.saas.cloudflare.uri");
        },
      },
    },
  } as PlatformSettings,
});
```

Interface names are the PascalCased path with a `Settings` suffix: `RedisSettings`,
`PlatformSaasCloudflareSettings`. Nodes get interfaces; leaves become properties, so the schema's
78 leaves produce no names at all and its 24 nodes produce 24.

The suffix is not decoration. Bare names collide: `History`, `Response` and `Storage` are global
types, and `Redis` and `Session` are exported by libraries already in use. `Config` is the wrong
suffix for these consumers specifically — `api` already uses it for a router's options bag
(`AcquisitionConfig`, `ManagementConfig`, `AdminConfig`), so `ApiConfig` would read as a handler's
options rather than the `api.*` group.

The names matter in one position only: naming a group in a signature, `function build(cf:
PlatformSaasCloudflareSettings)`. Everywhere else the type is inferred and never written.

**Getters, not values.** `init()` is awaited after modules are imported, so an object of resolved
values would snapshot before the config loads and hand back empty strings. A getter reads the
store when the property is touched, which is what `config.get` does today.

**A factory, not a bound object.** Two reasons. The generated file importing the config instance
while `config/index.ts` imports the generated types is a cycle; a factory imports nothing and is
trivially testable. And the destructuring is a feature, not upkeep: it names the roots this
service actually uses, which is worth having when one schema is shared across services. Unbound
groups cost nothing — every leaf is a getter, so nothing is read until it is touched.

The line changes only when a root group is added, removed or renamed — eleven exist today, so once
or twice a year. A new key, or a whole new `platform.<cloud>` branch, needs no edit.

`index.ts` binds once:

```ts
export const config = createConfig<ConfigKeys>({ schema, sources: [...] });
export const { platform, redis, observability } = bind(config);
```

Call sites then name no root and no string:

```ts
import { platform } from "@src/config";

new R2BlobStore({
  endpoint: platform.saas.cloudflare.uri,
  bucket: platform.saas.cloudflare.bucket,
});
```

## What the library has to grow

- `--branch <key>` on the `types` command, naming the branch node (`platform`).
- `pruneBranch(schema, branch, name)` in core, used by `createConfig` when given a branch
  selection, and by the generator so both see the same tree.
- Emission of per-node interfaces and the `bind` factory alongside `ConfigKeys`.

`get()`, `has()`, `explain()` and `toJSON()` are untouched. Strings remain the interface for
dynamic keys; the accessors are an ergonomic layer over them, not a replacement.

## Layer files

A layer file today sets the flattened path, because that is what the runtime resolved:

```json
{ "cloudflare": { "accountId": "..." } }
```

With keys keeping their path it would have to become
`{ "platform": { "saas": { "cloudflare": { "accountId": "..." } } } }`, which restates in the file
what the directory already says — layer files live in `config/saas/`. So `fileLayers` roots a
platform directory's values under `platform.<name>` itself, and the files do not change.

## Secret names under a branch

`secretNames()` derives a vault name from the key below `secret.`. Under a branch, the path is
`platform.saas.secret.cloudflareApiToken`, and the naive derivation gives
`platform-saas-secret-cloudflare-api-token` rather than `cloudflare-api-token`.

Every secret in both repos already sets `secretName` explicitly, so no vault changes and nothing
breaks. The rule for entries that omit it: derive from the path below the nearest `secret` node,
ignoring the branch prefix. An operator renaming existing secrets for readability does so as a
vault migration — new name added, deploy, old name removed — not as a code change.

## Migration

Additive for anyone not using a branch: no `--branch`, no pruning, `ConfigKeys` as before, and the
accessors are opt-in. For the two repos that do:

1. `scripts/config-types.mjs` deleted, both repos.
2. `overlay()` and `allPlatformsSchema()` deleted from `config/platform.ts`; what remains is
   `PLATFORMS`, `isPlatform`, `layersDir`.
3. The consumer test pinning generator-vs-runtime agreement deleted — the divergence it guards
   cannot occur once there is one implementation.
4. Provider builders move from `config.get("cloudflare.uri")` to `platform.saas.cloudflare.uri`.

`api` has a collision to settle first: `script/providers/index.ts` already exports `platform()`,
the provider bundle. Two different `platform` in one file, one callable and one not. The provider
function should be renamed — it was never a good name for something returning a set of seams.

## Alternatives considered

- **Keep flattening, teach the generator the same merge.** Removes the duplication but keeps deep
  overlay semantics, which is the part that drifted.
- **`$platforms: ["saas"]` tags instead of a branch node.** Also a filter, and keeps keys short,
  but scatters platform membership per group and loses the grouping the branch gives.
- **One `ConfigTree` interface, aliased where needed.** Fewer names, but the consumer wants to
  refer to a node without naming the root.
- **Schema as `as const` TypeScript, no codegen.** Never stale, but the schema stops being data,
  and enum inference and error messages both get worse.
- **Zod or TypeBox as the source of truth.** Answers a different question — whether this stays
  convict — and is a core rewrite.

## Open questions

1. Do the accessors carry `has`/`explain` per node, or do those stay string-keyed?
3. Version: this is additive to the core API, so a minor — but the emitted file's shape changes,
   which every consumer regenerates. Worth a major on the CLI's output format alone.
