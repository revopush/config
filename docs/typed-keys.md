# Typed keys

`config.get(key)` works with plain strings out of the box: `get<T>(key: string): T`, with `T`
inferred as `any` unless you annotate the call site. Generating a `ConfigKeys` interface from
`schema.json` turns that into a fully typed, autocompleted API — every key comes from the schema,
so a typo becomes a compile error instead of a `undefined` discovered at runtime.

## Why typed keys exist

Without generated types, `config.get("redis.port")` returns `any`, and a typo —
`config.get("redis.prot")` — compiles fine and fails only when that line actually runs, in
whichever environment happens to execute it first. With `ConfigKeys` passed as `createConfig`'s
type parameter, `get()` only accepts keys the schema actually declares, and the return type is
schema-derived (`number`, not `any`) — so the same typo is rejected by the compiler, and every
caller gets autocomplete instead of having to open `schema.json` to check a key's exact spelling.

## The command

The generator ships as a CLI binary, `revopush-config`, from the `@revopush/config` package:

```bash
npx revopush-config types --dir ./config --out ./src/config-keys.generated.ts
```

Run against a schema declaring `port`, an enum `logLevel`, a strict-boolean
`enableAccountRegistration`, a nullable `redis.port`, and a secret `secret.sessionSecret`, this
actually writes:

```ts
// Generated by `revopush-config types`. Do not edit.
// Re-run the generator after changing schema.json.

export interface ConfigKeys {
  /** HTTP port */
  port: number;
  /** Log verbosity */
  logLevel: "debug" | "info" | "warn";
  /** Whether new accounts can register */
  enableAccountRegistration: boolean;
  /** Redis port */
  "redis.port": number | null;
  /** Session signing secret */
  "secret.sessionSecret": string;
}
```

Pass `--interface` to name the interface something other than the default `ConfigKeys` — useful if
a service generates more than one, or the name collides with something else in scope:

```bash
npx revopush-config types --dir ./config --out ./src/config-keys.generated.ts --interface AppConfigKeys
```

```ts
export interface AppConfigKeys {
  /** HTTP port */
  "port": number;
  ...
}
```

## Using the output

Import the generated interface and pass it as `createConfig`'s type parameter. Everything else
about the call is unchanged — this is opt-in, not a second API:

```ts
// before: get<T>(key: string): T, T defaults to any
const config = createConfig({ schemaDir: "./config" });
await config.init();
const port = config.get<number>("port"); // you supply the type, and the key is just a string
```

```ts
// after: get<P extends keyof ConfigKeys>(key: P): ConfigKeys[P]
import { createConfig } from "@revopush/config";
import type { ConfigKeys } from "./config-keys.generated.js";

const config = createConfig<ConfigKeys>({ schemaDir: "./config" });
await config.init();
const port = config.get("port"); // inferred as number, no annotation needed
```

Compiled with `tsc --strict`, `config.get("port")` above infers as `number` and
`config.get("logLevel")` infers as `"debug" | "info" | "warn"`, with no other change to the call
site. A typo genuinely fails to compile:

```ts
config.get("por");
// error TS2345: Argument of type '"por"' is not assignable to parameter of type
// '"port" | "logLevel" | "enableAccountRegistration" | "redis.port" | "secret.sessionSecret"'.
```

That is the actual `tsc` output for the schema above — verified by compiling both the correct and
the typo'd call site.

## The mapping table

The emitter walks every schema leaf — any node carrying `default` — and maps it to a TypeScript
type:

| schema                                                                                          | TypeScript                                              |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `format` is an array, e.g. `["debug", "info", "warn"]`                                          | union of string literals: `"debug" \| "info" \| "warn"` |
| `format: "strict-boolean" \| "boolean" \| "Boolean"`, or a boolean `default`                    | `boolean`                                               |
| `format: "port" \| "int" \| "nat" \| "duration" \| "number" \| "Number"`, or a number `default` | `number`                                                |
| anything else                                                                                   | `string`                                                |
| `nullable: true`, or `default: null`                                                            | appends `\| null` to whatever the above produced        |
| `required: true`                                                                                | no effect — the default's type is still what is emitted |
| `tsType: "..."` present                                                                         | overrides everything above — see below                  |

The nullable rule composes with every other row: a nullable numeric key becomes `number | null` (as
`redis.port` does in the example above, from `"nullable": true` with `format: "port"`), and a
nullable key with `default: null` gets the same treatment even without an explicit `nullable: true`.

## `tsType` is trusted, unvalidated input

`tsType` is the escape hatch for a custom format the emitter has no built-in mapping for — set it
and it replaces the inferred type entirely (nullable handling still applies on top of it). It is
injected **verbatim** into the generated `.ts` file with no validation:

```json
{
  "cursor": {
    "doc": "Pagination cursor",
    "default": "",
    "format": "my-cursor-format",
    "tsType": "0 | 1"
  }
}
```

generates `"cursor": 0 | 1;` exactly as given. There is no check that the string you pass is valid
TypeScript — a malformed value (mismatched brackets, a typo, anything that isn't a syntactically
valid type expression) is copied straight into the output and produces broken TypeScript, caught
only when something tries to compile the generated file. Treat `tsType` the way you'd treat any
other string that ends up unescaped in generated code: correct by construction, not by validation.

## `--check` in CI

`--check` compares the schema against the already-generated file instead of rewriting it, and exits
non-zero the moment they disagree — this is what stops the generated types from silently drifting
away from `schema.json` as the schema evolves.

Run against the file generated above, with nothing changed:

```bash
$ npx revopush-config types --dir ./config --out ./src/config-keys.generated.ts --check
./src/config-keys.generated.ts is up to date.
```

exits `0`. After adding an undeclared key to the schema without regenerating:

```bash
$ npx revopush-config types --dir ./config --out ./src/config-keys.generated.ts --check
./src/config-keys.generated.ts is out of date. Re-run without --check to regenerate.
```

exits `1` — both lines are the literal output from running it.

As a CI step, placed after `schema.json` is available and before anything that depends on the
generated types compiling:

```yaml
- run: npx revopush-config types --dir ./config --out ./src/config-keys.generated.ts --check
```

Without this step in CI, nothing stops `schema.json` and the generated file from diverging: someone
adds, renames, or retypes a schema key, forgets to regenerate, and the change ships. The generated
file keeps compiling — TypeScript has no way to know it's wrong — but it is now silently lying about
the configuration: a key it claims is `number` might no longer exist, or a key that does exist might
be missing from the type entirely. That is worse than shipping without generated types at all, since
nothing signals the mismatch until a caller hits it at runtime, exactly the failure mode typed keys
exist to prevent.
